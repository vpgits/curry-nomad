Two auth planes, kept separate:

Plane 1 — identity. Aegra AUTH_TYPE=custom + auth.py verify the NextAuth HS256 session JWT (per-operator thread scoping).

Plane 2 — authorization. A separate incremental Google grant; the access token rides per-run in config.configurable.google_access_token.

Async-only MCP tools. langchain-mcp-adapters exposes coroutine-only tools — a sync .invoke() raises "StructuredTool does not support sync invocation". The runner drives the loop with asyncio.run(agent.ainvoke(...)). This still streams token-by-token (verified end-to-end): LangChain streaming is callback-based, the handlers ride in config, and they're thread-safe — the inner event loop doesn't detach them. Tokens arrive under a workspace:… subgraph namespace, so streamSubgraphs:true clients render them inline like analytics.

Could this be one orchestrator agent with the capabilities as nodes?

router → supervisor

Yes — that's the supervisor pattern, and LangGraph supports it. But the docs draw a sharp line: "a supervisor is a full agent that dynamically decides which subagents to call across multiple turns; a router is a single classification step that dispatches without ongoing state." Nora today is a router (classify once → one capability → END), so it can't compose ("analyze sales then make an ad for the winner" = two turns). Below are four ways to evolve it, with the trade-offs that actually matter for this codebase.

The Nora-specific catch that rules out the simplest option: the docs warn that subagents called as tools are not statically discoverable — get_state(subgraphs=True) can't see their interrupt state, and "to read nested graph state during an interrupt, invoke the subagent from a node function in a custom graph instead." Nora leans hard on exactly that (marketing HITL gates + useStream resume, and native subgraph-namespace gen-UI streaming). So the tidy "everything is a tool" supervisor (Option A) is the worst fit for Nora's HITL/gen-UI — which pushes toward keeping capabilities as graph nodes (Options B/C).

Recommendation for Nora: if you want a single orchestrating agent that composes capabilities, go Option B (agents-as-nodes + Command(goto) handoff) — it's the exact form the docs point to when "a node is itself a complex graph with reflection" (marketing's evaluator loop) and when you "need to read nested interrupt state." It keeps streaming, HITL, gen-UI, and the deterministic-ops pillar intact, and only adds a small supervisor node + an active/plan state field. Option C is the most teaching-appropriate middle ground (one planning call, deterministic execution, an inspectable plan). And per LangChain's own "start simple — add dynamics only when needed": if single-intent-per-turn is acceptable, Option 0 (today's router) is still correct — don't buy agency you don't need. The one option to avoid for Nora specifically is the tools-only supervisor (A), because it forfeits the interrupt-state visibility and subgraph-namespace streaming the app is built on.
Migration cost (B), concretely: add a supervisor node and a plan: list[str] / step: int (or active) field to OrchestratorState; change each capability's terminal edge from → END to → supervisor; the supervisor advances the plan and emits Command(goto=next | END). Capabilities stay byte-for-byte the same compiled subgraphs/nodes — only the wiring around them changes. Mind the docs' context-hygiene rule: pass only a compact summary of each capability's result back to the supervisor, not the full sub-thread.

Alignment with LangChain's published guidance

docs.langchain.com

Read from the LangChain docs MCP — Workflows & agents, Streaming, Human-in-the-loop, Multi-agent patterns, Context engineering. The codebase tracks the recommended patterns closely; one real gap.

Workflow vs. agent ✓ textbook

"Workflows have predetermined code paths… Agents are dynamic and define their own processes and tool usage."

Their five patterns — chaining, parallelization, routing, orchestrator-worker, evaluator-optimizer — are all present: analytics = agent, marketing = chaining + parallel + evaluator loop, route = routing.

Nodes can be functions, LLM calls, or whole agents ✓

"Each node can be a simple function, an LLM call, or an entire agent with tools… mixing deterministic logic and agentic behavior."

The orchestrator does exactly this: route (LLM), analytics/workspace (agents), marketing (workflow), routing (plain function).

Streaming "from any part of the graph" ✓ verified

"Use messages mode to stream LLM outputs token-by-token from any part of your graph, including nodes, tools, subgraphs" (+ subgraphs=True).

Both analytics and workspace stream token-by-token (tested end-to-end). Streaming is callback-based: the handlers ride in config, so workspace's asyncio.run(agent.ainvoke(…, config)) does not detach them (they're thread-safe, not loop-bound). Tokens arrive under a workspace:… subgraph namespace; clients just need subgraphs=True (the web app's streamSubgraphs:true).

Keep internal calls off the stream ✓

"Use the nostream tag to exclude LLM output… when you stream the same content through a different channel and want to avoid duplicate output."

Router, dashboard, a2ui-author and marketing all set disable_streaming=True for exactly this reason — their structured outputs are consumed into state, not shown as chat.

Human-in-the-loop & bubbling ✓

"For nested subgraphs, read message chunks from stream.subgraphs[*].messages"; resume with Command(resume=…). Static breakpoints are "not recommended for HITL".

Marketing uses dynamic interrupt() (not breakpoints); the config pass-through bubbles the gate up through the orchestrator; the web resumes via useStream's stream.interrupt.

Context engineering — "add dynamics only when needed" ✓

"Start simple — begin with static prompts and tools, add dynamics only when needed."

Tools are bound statically everywhere except workspace, where they're genuinely token-dependent (per-operator MCP). That's the rule applied, not over-applied.
